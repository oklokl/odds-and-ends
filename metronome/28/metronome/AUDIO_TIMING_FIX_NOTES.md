# 메트로놈 오디오 타이밍 문제 분석 및 수정 기록

작성 기준: 2026-09-28

이 문서는 다시 같은 문제를 만들지 않기 위한 기술 기록입니다. 단순 변경 내역이 아니라 **증상 → 오판하기 쉬운 지점 → 실제 원인 후보 → 최종 해결 구조 → 앞으로 건드릴 때의 주의점** 순서로 정리합니다.

---

# 1. 사용자가 실제로 들은 증상

대표 증상은 다음과 같았습니다.

```text
정상:   단 - 다 - 다 - 다 - 다 - 다 - 다 - 단 ...
이상:   단 - 다다다 - 단다단다 - (잠시 정상) - 다시 몰림 ...
```

특히 다음 특징이 중요했습니다.

- 강박 직전 1~2박이 갑자기 빨라진 것처럼 들림
- 강박이 늦거나 그냥 지나간 것처럼 느껴질 때가 있음
- 일정 시간은 정상인데 갑자기 리듬이 생김
- 소리끼리 겹치는 것 자체가 핵심 문제가 아니었음
- 화면상의 BPM/박자 계산은 정상으로 보임
- 기계적인 메트로놈이어야 하는데 사람처럼 "리듬을 타는" 느낌이 생김

이 패턴은 단순 BPM 수식 오류보다 **오디오 시작 시점의 지터(jitter) 또는 타이머 catch-up**을 의심해야 하는 증상입니다.

---

# 2. 첫 번째로 의심했던 부분

기존 타이머가 목표 시각에 늦으면 다음 박에서 원래 시간표를 따라잡으려는 동작이 있었습니다.

예를 들어 원래 250ms 간격이어야 할 때:

```text
0ms
250ms
500ms  ← 이 박이 실제로 520ms에 실행됨
750ms  ← 원래 시간표를 따라잡으려 하면 다음 간격은 230ms
```

귀에는 다음처럼 들릴 수 있습니다.

```text
... 느려짐 → 갑자기 빨라짐 → 다시 정상
```

그래서 `MetronomeService.kt`에는 다음 방어를 넣었습니다.

- 목표보다 조금 일찍 Handler를 깨움
- 마지막 짧은 구간을 정밀 대기
- 2ms 이상 크게 늦으면 다음 박에서 무리하게 catch-up하지 않고 현재 시각을 새 기준점으로 잡음
- 재생 중 WakeLock을 유지하여 절전 영향 완화

이 수정은 옳았지만, **이것만으로 실제 소리 문제는 완전히 없어지지 않았습니다.**

이 사실이 최종 원인을 좁히는 중요한 단서였습니다.

---

# 3. 핵심 문제: "정확한 타이머"와 "정확한 소리 출력"은 다르다

예전 구조는 개념적으로 다음과 같았습니다.

```text
Handler/Thread가 박 시각 계산
        ↓
매 박마다 SoundPool.play()
        ↓
Android 오디오 시스템
        ↓
실제 소리 출력
```

타이머 호출이 정확하더라도 `play()`를 매번 별도 요청하면 실제 오디오 출력 시점은 다음 요소의 영향을 받을 수 있습니다.

- 스레드 스케줄링
- 순간 CPU 부하
- GC 및 앱 내부 작업
- 오디오 믹서/버퍼 상태
- 각 재생 요청의 큐잉 시점
- 압축 사운드 처리
- 파일별 선행 무음

즉 다음 두 값은 같지 않습니다.

```text
"play()를 호출한 시각" != "스피커에서 transient가 실제 시작한 시각"
```

메트로놈에서는 이 차이가 반복될 때 매우 잘 들립니다.

---

# 4. MP3도 보조 원인이 될 수 있었음

원본 MP3를 조사했을 때 일부 사운드 세트에서 강박/약박의 실제 타격 전 선행 무음 길이가 서로 달랐습니다.

MP3는 다음 이유로 메트로놈용 원천 샘플로는 덜 단순합니다.

- 압축 디코딩 과정이 있음
- 인코더 delay/padding이 존재할 수 있음
- 파일마다 transient 앞의 무음이 다를 수 있음
- 매번 독립 재생하면 이런 차이가 박자 체감에 직접 반영됨

하지만 여기서 중요한 결론은:

> **"MP3라서 문제였다"가 전부가 아니다.**

WAV로 바꿔 놓고도 매 박마다 Java 타이머로 개별 재생을 요청한다면 시스템 부하에 따른 지터 문제는 남을 수 있습니다.

최종 해결의 핵심은 **PCM WAV + AudioTrack 연속 재생 구조**입니다.

---

# 5. 최종 해결 구조

현재 `SoundManager.kt`의 구조는 다음과 같습니다.

```text
strong_pcm.wav ─┐
                 ├─> 한 마디 PCM 버퍼 미리 합성 ─> AudioTrack ─> 무한 루프
weak_pcm.wav   ──┘
```

매 박마다 `play()`를 호출하지 않습니다.

## 5-1. WAV 로딩

`readPcmWav()`에서 파일을 직접 읽고 형식을 검증합니다.

필수 조건:

- RIFF/WAVE
- PCM format = 1
- 48,000 Hz
- Stereo
- 16-bit

잘못된 파일을 조용히 억지로 재생하지 않고 로딩 단계에서 실패시키는 것이 중요합니다. 그래야 "왠지 박자가 이상한데 이유를 모르는" 상황을 줄일 수 있습니다.

## 5-2. 한 박 위치 계산

현재 핵심 계산식:

```text
framesPerBeatExact = 48000 × 60 / BPM × (4 / Unit)
```

박 번호 `n`의 시작 프레임:

```text
round(framesPerBeatExact × n)
```

누적 정수 덧셈이 아니라 각 위치를 Double 기준으로 다시 계산하고 반올림하므로 fractional frame 때문에 생길 수 있는 장기 누적 오차를 줄입니다.

## 5-3. 한 마디 전체 합성

- 첫 박: `strong_pcm.wav`
- 나머지 박: `weak_pcm.wav`
- 각 소리를 미리 계산된 샘플 프레임 위치에 섞음
- 소리의 tail이 다음 박 또는 다음 마디로 넘어갈 수 있도록 원형 버퍼에 합성
- 겹칠 때 Short overflow를 막기 위해 saturating add 사용

즉 소리가 겹치는 것을 문제로 보지 않고 **타격 시작 시각을 정확히 고정하는 것**을 우선했습니다.

## 5-4. MODE_STATIC 우선

일반적인 마디는 전체 PCM을 한 번 `AudioTrack.MODE_STATIC`에 기록한 뒤:

```text
setLoopPoints(0, frameCount, -1)
```

으로 네이티브 오디오 레이어에서 무한 반복합니다.

장점:

- 매 박 Java callback 불필요
- 매 박 객체 생성/디코딩 불필요
- 오디오 샘플 자체가 시간축
- CPU/UI 순간 부하와 실제 박 출력의 결합이 크게 줄어듦

## 5-5. MODE_STREAM 폴백

마디 PCM이 너무 크거나 특정 기기에서 MODE_STATIC 생성이 실패하면 `MODE_STREAM`으로 같은 완성된 PCM 마디를 계속 씁니다.

여기서도 중요한 점은:

> MODE_STREAM 폴백조차 "박마다 소리 재생"이 아니라 "이미 만들어진 연속 PCM"을 공급합니다.

따라서 과거 방식으로 회귀하지 않습니다.

# 6. MetronomeService의 역할 분리

현재 일반 소리 재생 시:

```text
AudioTrack       = 실제 박자 소리
HandlerThread    = UI/현재 박 표시/플래시/진동 관련 틱
```

이 역할 분리가 매우 중요합니다.

화면 애니메이션이 한 프레임 늦거나 플래시 IPC가 늦어져도 **오디오 클릭은 계속 AudioTrack 시간축을 따라갑니다.**

플래시는 메인 Handler에 비동기로 보냅니다. 카메라 서비스 IPC가 오디오 출력 경로를 막지 않게 하기 위함입니다.

주의:

- 플래시와 화면은 오디오 샘플 정확도를 보장하는 계측기가 아닙니다.
- 진동 모드는 오디오와 달리 OS 진동 스케줄링 특성의 영향을 받을 수 있습니다.
- 소리 정확도를 판단할 때는 실제 오디오를 기준으로 해야 합니다.

---

# 7. 7/8, 120 BPM의 현재 앱 동작

현재 계산 방식에서 Unit=8은 4분음표 기준 BPM을 8분음표 간격으로 환산합니다.

```text
60 / 120 × (4 / 8)
= 0.25초
= 250ms
```

48 kHz에서는:

```text
48,000 × 0.25 = 12,000 frames / beat
```

7박이면:

```text
12,000 × 7 = 84,000 frames
= 1.75초 / measure
```

따라서 한 마디는 정확히:

```text
0      12000   24000   36000   48000   60000   72000   84000
강       약       약       약       약       약       약      다음 강
```

프레임 위치에 의해 결정됩니다.

# 8. 다시 건드릴 때 가장 위험한 변경

다음 변경은 타이밍 문제를 재발시킬 가능성이 큽니다.

## 금지 1: 매 박마다 `SoundPool.play()` 복원

```text
onTick() -> play(strong/weak)
```

이 구조로 돌아가면 이번 수정의 핵심 이점이 사라집니다.

## 금지 2: UI 애니메이션과 실제 오디오를 같은 Handler에 종속

Compose recomposition, 알림 업데이트, SharedPreferences, 카메라 플래시 등은 모두 오디오보다 느리거나 불규칙할 수 있습니다.

## 금지 3: MP3만 추가하고 자동으로 재생될 거라고 가정

현재 엔진은 `_pcm.wav`를 읽습니다.

## 금지 4: WAV 이름만 맞추고 포맷을 확인하지 않음

`.wav`라는 확장자만으로 PCM16/48kHz/Stereo가 보장되지 않습니다.

## 금지 5: 사운드 앞부분의 무음을 방치

10~100ms의 앞 무음은 코드의 박 위치가 정확해도 실제 클릭을 늦게 느끼게 만듭니다.

## 금지 6: 오디오 재생 중 무거운 작업을 오디오 스레드에 추가

파일 I/O, 로그 폭주, 이미지 처리, 네트워크, DB, 설정 저장 등을 넣지 마십시오.

# 9. 앞으로 문제가 생기면 확인할 순서

1. 같은 WAV로 set0에서 재현되는가?
2. BPM/Beat/Unit 특정 조합에서만 재현되는가?
3. 앱 화면이 멈춰도 실제 오디오는 일정한가?
4. 유선/블루투스/폰 스피커 중 특정 출력에서만 생기는가?
5. BPM을 변경하는 순간만 이상한가, 변경하지 않아도 지속적으로 이상한가?
6. `AudioTrack`이 MODE_STATIC을 썼는지 STREAM 폴백을 탔는지 로그 확인
7. WAV 앞쪽 무음과 transient 위치 확인
8. CPU/GC 문제가 아니라 오디오 데이터 자체에 리듬이 들어간 것은 아닌지 파형 확인

특히 Bluetooth는 코덱 버퍼링 때문에 전체 지연(latency)은 커질 수 있습니다. 그러나 정상적인 연속 PCM에서는 **박 간격 자체는 일정해야** 합니다. 절대 지연과 박자 지터는 다른 문제입니다.

# 10. 최종 결론

이번 문제의 핵심은 "BPM 계산식 하나"가 아니었습니다.

최종적으로 안정화된 이유는:

```text
MP3/SoundPool/박별 호출
        ↓
PCM WAV/한 마디 사전 합성/AudioTrack 연속 루프
```

로 오디오 아키텍처를 바꿨기 때문입니다.

한 줄로 기억하면 됩니다.

> **메트로놈의 실제 시간축은 Java 타이머가 아니라 오디오 샘플 자체가 담당해야 한다.**
